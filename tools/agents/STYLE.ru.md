# Стиль Zazzzor

[English (основная версия)](STYLE.md)

Все правила появились на ревью кода этого репозитория. Если на ревью обнаружится новая повторяющаяся ошибка, добавьте правило сюда. Перед коммитом проверьте по этому списку свой diff.

Правила идут в порядке важности.

---

## 1. Сначала ищите, что можно переиспользовать

Прежде чем добавлять вспомогательную функцию, клиент, скрипт или загрузчик конфигурации, поищите готовый вариант командой `rg -n "func load_env|smokeSession|NewService\(" server deploy`. Расширьте существующий вариант или перенесите туда, откуда им смогут пользоваться оба вызывающих модуля. Избегайте копий.

- ❌ `deploy/scripts/env.sh` с копией `load_env` из `stack.sh`.
- ❌ `deploy/tests/restore-data.go` со вторым HTTP-клиентом рядом с командой `smoke`.
- ✅ Скрипты запускают Go-код, уже включённый в образ, через `exec docker exec "$swarm_api" /zazzzor smoke "$base_url"`. Расширьте `smokeSession` в `server/cmd/zazzzor/smoke.go`. Общий код Bash вынесите в файл, который оба скрипта подключают через `source`.

## 2. Go-код хранится в модуле

Каждая точка входа Go — подкоманда `server/cmd/zazzzor` (`healthcheck`, `smoke`, `files …`). Скрипты вызывают этот бинарный файл. Для Go-файлов за пределами `server/` не запускаются Go vet, линтеры и тесты.

## 3. Тестовые настройки не должны попадать в рабочий API

- ❌ Неэкспортируемое поле `heartbeatInterval` в экспортируемом `Options`, доступное через `export_test.go` только для ускорения тестового времени.
- ✅ Проверяйте поведение через имеющиеся настройки. Шлюз контролирует только `HeartbeatTimeout`, поэтому тесты задают его. Если нужно подменить время, пакет принимает `Now func() time.Time` или часы в `Options`. Так уже делают `auth.Options` и `guilds.Options`, где `Now` по умолчанию использует `time.Now`.

## 4. Один конструктор с сигнатурой `NewX(Options)` и один блок `const` для значений по умолчанию

- ❌ `NewDiskWithOptions` и `DiskOptions` рядом с `NewDisk`.
- ❌ Строка `"192h"` в пяти местах.
- ✅ `guilds.NewService(guilds.Options{Pool: pool, IDs: ids, …})`. Конструктор `NewX` подставляет значения по умолчанию для полей с нулевым значением.
- ✅ Значения по умолчанию — именованные константы в блоке `const` пакета, как в `config.go`:

  ```go
  const (
  	DefaultHTTPAddr = ":8080"
  	DefaultDataDir  = "/data"
  )
  ```

  Код обращается к константам. Документация и `.env.example` опираются на те же константы. Укажите значение в документации один раз и назовите источник.

## 5. Инварианты, зависящие только от кода, не требуют `panic`

Для настроек подставляйте значения по умолчанию. Проверяйте данные извне, например переменные окружения и запросы, и возвращайте ошибки. Связь между двумя константами проверяйте тестом.

## 6. Оборачивайте каждую возвращаемую ошибку в `pkg: what: %w`

- ❌ Голый `return err` или `fmt.Errorf("failed")` без глагола, описывающего действие.
- ✅ `return fmt.Errorf("files: create temp file: %w", err)` из функции `write` в `files.go`.

Объявляйте ошибки-сентинелы через `var ErrX = errors.New("pkg: …")`. В вызывающем коде проверяйте их через `errors.Is`.

## 7. Сообщайте настоящую причину сбоя

- ❌ `mkdir "$dir/.lock" 2>/dev/null || fail 'another backup … holds .lock'`. И ошибка прав доступа, и устаревшая блокировка выглядят как выполняющееся резервное копирование.
- ✅ Проверьте состояние и сообщите, как его исправить, как делает `require_swarm` в `stack.sh`:

  ```bash
  die "Docker не в режиме Swarm (состояние: ${state:-неизвестно}). Включите его: docker swarm init"
  ```

  Если операция может завершиться ошибкой по разным причинам, сохраняйте вывод stderr.

## 8. Автономные задачи должны переживать сбои и сообщать о своём состоянии

Запланированная задача должна:

- переживать собственный сбой. Используйте `flock` и избегайте каталогов-блокировок;
- проверять условия запуска, в том числе доступность каталога для записи и свободное место, и сообщать, какое условие нарушено;
- давать проверке состояния способ определить актуальность результата, например по возрасту последней резервной копии.

Если задача прекращает работу, об этом должен быть сигнал.

## 9. Документирующий комментарий описывает поведение каждого нетривиального идентификатора

- Добавляйте комментарий к каждому экспортируемому идентификатору и каждой нетривиальной неэкспортируемой функции. Простым английским языком опишите, что делает код и зачем.
- Синхронизируйте документацию пакета (`doc.go` или комментарий к пакету) с его структурой.
- ✅ Пример из `files.go`:

  ```go
  // syncDir makes the rename durable where the platform allows it (Unix);
  // failure only weakens durability after a crash, so it is ignored.
  ```

- Описывайте поведение, избегая рассказов об изменениях вроде «теперь мы…» и «добавлено…». Соблюдайте принятую плотность комментариев.

## 10. Один сценарий на тест, внешний пакет, общие помощники и формат `got = …, want …`

- Используйте пакет `pkg_test`. Если нужен доступ к внутренностям пакета, назовите файл `*_internal_test.go`.
- Переиспользуйте помощники пакета, например `envFrom` из `config_test.go`, `newDisk` из `files_test.go` или `newEnv` из тестов шлюза. Помощники вызывают `t.Helper()`.
- Сообщения следуют формату `X = %v, want %v`. Для фатальной ошибки указывайте контекст через `t.Fatalf("Load: %v", err)` вместо голого `t.Fatal(err)`.
- Каждый тест покрывает один сценарий. Укажите его в имени, например `TestReconcileKeepsReferencedFiles` вместо `TestReconcile`.
- ❌ Проверка значения константы через `HeartbeatInterval != 30*time.Second`. Проверяйте поведение, например какое значение по умолчанию применяет `New` или какую задержку допускает тайм-аут.
- Передавайте часы в код и по возможности избегайте `time.Sleep`. Если необходимо реальное время, как в шлюзе, сократите интервалы и оставьте достаточный запас.
- Сначала напишите падающий тест и убедитесь, что он падает по ожидаемой причине. Затем исправьте реализацию.

## 11. Подавляйте предупреждение линтера на строке, к которой оно относится, и указывайте причину

✅ Поместите `//nolint:gosec // G304: dir is built from validated components.` прямо у `os.Open(dir)`. Если возникает новое замечание, исправьте его причину. Перенос старого подавления на непричастную строку скрывает проблему.

## 12. Оформляйте скрипты по образцу `deploy/scripts/stack.sh`

- Используйте `#!/usr/bin/env bash` и `set -euo pipefail`. Выбирайте Bash. Скрипт внутри образа BusyBox или Alpine может использовать POSIX sh. Укажите это в заголовке и протестируйте скрипт в этом образе.
- Заголовок на английском объясняет назначение скрипта. В блоке `Usage` перечислите все команды и переменные. Справку для пользователя можно локализовать, сохраняя существующий формат вывода; руководства по эксплуатации доступны на обоих языках.
- Пишите по одному выражению на строку. Над каждой функцией и каждым неочевидным шагом объясняйте в комментарии, зачем он нужен.
- Сообщение об ошибке подсказывает, как её исправить. Выводите его через `die` (код завершения 2). Для новых сообщений основной язык — английский. Сохраняйте диагностические сообщения существующих скриптов, пока их не проверили.
- Заключайте каждую подстановку в кавычки. Для списков аргументов используйте массивы.
- Сделайте скрипт исполняемым в Git через `git update-index --chmod=+x path`. Команда `git ls-files -s path` должна показать режим 100755.
- Запустите `shellcheck -x` и устраните замечания. Скрипт проверок также запускает эту команду.

## 13. Пишите короткие пронумерованные руководства для владельца на двух языках

Поддерживайте [основное руководство](../../deploy/README.md) на английском и [перевод](../../deploy/README.ru.md) на русском. Используйте короткие предложения, пронумерованные шаги и блоки `bash` для команд. Предупреждение ставьте перед любым разрушительным действием. Каждую новую переменную объявляйте в общем файле `.env.example` один раз и сопровождайте однострочными комментариями на английском и русском, в таком порядке.

## 14. Один коммит на логическое изменение, с описанием неочевидной причины

- ❌ Два коммита для четырёх логических изменений. ❌ Коммит на 870 строк, объединяющий развёртывание, CI, скрипты и документацию. ❌ `fix(server): …` без тела сообщения при изменении архитектуры.
- ✅ `b0c6518`:

  ```
  fix(server): make sending a message safe to retry

  Create and Edit read the author and the replied-to message before the
  write, so nothing can fail between storing a message and announcing it.
  ```

- В теле сообщения объясняйте, зачем нужно изменение, и указывайте решения, которые ревьюеру пришлось бы выяснять самостоятельно. Переносите строки на 72-м столбце.
- Если задача предполагает разделение на коммиты, придерживайтесь его или объясните причины в pull request.

## 15. Восстановление и обновление — часть функциональности

Для резервного копирования, миграций, сверки и любых других операций, меняющих данные, определите:

- что произойдёт при запуске с более новой или старой схемой;
- что произойдёт, если приложение работает одновременно с операцией;
- что произойдёт, если повреждён один элемент.

Ошибочный элемент пропускайте, записывайте в журнал и указывайте в отчёте, чтобы обработка продолжалась. Если на данные всё ещё могут ссылаться, сохраняйте их в течение льготного периода. Отсчитывайте его от *времени начала обработки*.

## 16. Необязательные настройки в `.env.example` закомментированы

`load_env` берёт **первое** значение ключа, а Compose — последнее. Поэтому активная строка в примере перекрывает значение, которое владелец допишет позже. Новые переключатели и переменные для отдельного варианта развёртывания оставляйте закомментированными, указывая значение по умолчанию. В документации просите «раскомментировать и изменить» строку.

- ❌ Активные строки `ZAZZZOR_EDGE=caddy` и `TRAEFIK_SUBNET=` (C3).
- ✅ Пример:

  ```
  # How long deleted images stay in the trash. Use more than one day (192h = 8 days).
  # Сколько удалённые картинки лежат в корзине; больше суток (192h = 8 суток).
  # ZAZZZOR_FILE_RETENTION=192h
  ```

## 17. Для изменения развёртывания нужен переход с текущей конфигурации

Если изменение заменяет что-то из того, что уже запущено у владельца, документация должна показать соответствие **старое → новое** для каждой переменной, секрета и тома. Используйте существующие секреты повторно, например пароль базы данных, который уже хранится в томе. Предпочитайте обновление на месте через `stack deploy`, без `stack rm`, простоя или резервного копирования вручную. Например, для изменения свойств сети создайте сеть с новым именем.

## 18. Выясните причину предупреждения линтера перед подавлением

Причина подавления должна объяснять реальную проблему, подтверждённую воспроизведением. Недостаточно указать, что предупреждение появилось после подключения компонента.

- ❌ `//nolint:contextcheck` у `m.NewGateway(...)` «из-за подключения LiveKit SDK» (C4). Причина была в давнем коде: `hub.dispatch` создавал контекст из поля `g.ctx`, не принимая ctx параметром.
- ✅ При передаче контекста параметром (`dispatchLoop(ctx)`, `consume(ctx, …)`) предупреждение исчезает.

## 19. Записывайте ключи идемпотентности только после успеха

Если записать ключ заранее, повторный запрос после сбоя будет молча пропущен. Записывайте ключ после успешной операции или удаляйте его при ошибке. Проверьте тестом повторную попытку после ответа 500.

## 20. Для каждой проверки конкурентного доступа нужен тест, который без неё падает

Каждая проверка ревизии, SID, поколения и условие «пропустить, если пользователь подключился заново» требуют теста с нужным порядком событий, заданным блокирующей заглушкой. Удаление проверки должно приводить к падению теста.

## 21. После отклонённого коммита файлы остаются в индексе

Если хук отклоняет коммит, подготовленные файлы остаются в индексе. Следующий `git commit` может включить их в постороннее изменение. После каждого отклонённого коммита запустите `git status` и исправьте сообщение, прежде чем добавлять в индекс другие файлы. Перед выполнением следующей части последовательности `git commit … && git add … && git commit …` проверяйте, что первый коммит состоялся.

## 22. В тестах используйте разрешённые фиктивные учётные данные

Если тест требует секрет, используйте `0123456789abcdef0123456789abcdef`. В `.gitleaks.toml` разрешено только это значение. Оно состоит из 32 символов, как требует LiveKit. Любой другой ключ, похожий на настоящий, провалит проверку секретов. После отправки ветки CI упадёт во всех открытых pull request.

## 23. Обратный запрос отменяет отложенное действие

Если операция планирует отложенное действие, например резервное перемещение или удаление, обратный запрос должен его отменить. Это может быть возврат, удаление места назначения или потеря разрешения. Даже после ответа «без изменений, 204» ранее запланированное действие должно отмениться. В тесте отправьте запрос и обратный запрос, переведите часы за срок выполнения и убедитесь, что ничего не произошло.

## 24. Ограничивайте закрепление нужным сеансом

Для защиты одного закреплённого сеанса проверяйте исключение, например через `s.moves`. Обнуление общего состояния пользователя, например намерения токена, мешает корректно снять закрепление.

## 25. Проверяйте §20 удалением каждой проверки

Перед сдачей работы поочерёдно удалите каждую проверку конкурентного доступа или авторизации во временной копии и запустите тесты пакета. Если тесты проходят без проверки, добавьте тест или удалите лишнюю проверку. Если проверка служит дополнительным рубежом защиты, укажите это в комментарии.

## 26. Во всех операциях над другим участником проверяйте иерархию ролей

По §5 спецификации действие над другим участником допустимо только тогда, когда ваша высшая роль выше его высшей роли. Владелец может выполнять действия над любым участником. Используйте `permissions.CanActOn` вместе с проверкой разрешения и возвращайте `403 role_hierarchy`, как при исключении и блокировке.

## 27. Повторяйте критичное для безопасности удаление до срабатывания резервной проверки

Если повторы исчерпаны до очередной сверки, удалённый участник может оставаться подключённым в промежутке. Продолжайте попытки с ограничением максимальной задержки или запускайте сверку раньше.

## 28. Гарантируйте безопасность при панике только с отложенным снятием блокировок

Если тест подтверждает, что при панике владение освобождается, все блокировки на этом пути должны сниматься через `defer`. Если это не так, укажите границу гарантии.
